# bomcensus-manager

Helm chart for `bomcensus-server`: console, administrative API (port 8080) and agent gateway (port 8443). It can create its PostgreSQL database with CloudNativePG and install the in-cluster scanner (`bomcensus-scanner` chart) pre-wired to the agent Service.

Objects are named after the release: `<release>` (Deployment), `<release>-web`, `<release>-agent` (Services), `<release>-master-key`, `<release>-admin`, `<release>-database` (Secrets).

## Install

```sh
# argon2id hash of the console password (the chart cannot compute it)
printf '%s\n' 'the password' | docker run --rm -i bomcensus/server:VERSION hash-password > hash.txt

cat > values.local.yaml <<EOF
admin:
  passwordHash: '$(cat hash.txt)'
cnpg:
  cluster:
    create: true
scanner:
  enabled: true
EOF

helm dependency build deploy/charts/bomcensus-manager
helm install bomcensus deploy/charts/bomcensus-manager -n bomcensus --create-namespace \
  -f values.local.yaml --wait --timeout 15m
```

Pass the hash in a values file. With `--set` the commas in `m=65536,t=3,p=4` split the value; escape them (`\,`) if `--set-string` must be used.

## Database

Exactly one of:

| Mode | Values | The server reads `BOMCENSUS_DATABASE_URL` from |
|---|---|---|
| URL | `database.url` | Secret `<release>-database`, key `url` |
| Existing Secret | `database.existingSecret.name`, `.key` (default `url`) | that Secret |
| New CloudNativePG Cluster | `cnpg.cluster.create=true` | Secret `<cluster>-app`, key `uri`, generated by the operator for the `initdb` owner |
| Database in an existing CloudNativePG Cluster | `cnpg.database.create=true`, `cnpg.database.cluster`, `cnpg.database.namespace` | Secret `<release>-database`, key `url`, built by the chart |

The CloudNativePG modes need the operator's CRDs; the chart checks `.Capabilities.APIVersions` and fails with a message when they are missing (for `helm template`, pass `--api-versions postgresql.cnpg.io/v1/Cluster` and so on). Checked against CloudNativePG 1.30.2.

With `cnpg.cluster.create=true` the chart creates a `Cluster` (`instances`, `storage.size`, `storage.storageClass`, `imageName` (operator default when empty), `parameters`, `resources`, `affinity`) bootstrapped with `initdb` (`database`, `owner`). The server restarts until the cluster accepts connections, which takes a minute or two on a first install.

With `cnpg.database.create=true` the chart creates, in the namespace of the existing Cluster:

- a `kubernetes.io/basic-auth` Secret `<release-namespace>-<release>-role` with the owner name and a generated password (kept across upgrades), labelled `cnpg.io/reload: "true"`;
- a `DatabaseRole` (CloudNativePG 1.30 or later) for the owner with `login: true` and that password Secret;
- a `Database` (`name`, `owner`, `databaseReclaimPolicy`).

The database and the role default to `bomcensus_<release>`. `cnpg.database.reclaimPolicy` sets both `databaseReclaimPolicy` and `databaseRoleReclaimPolicy` (`retain` by default; `delete` drops them when the release is removed).

With an operator older than 1.30 there is no `DatabaseRole`. Set `cnpg.database.createRole=false` and add the role to the Cluster yourself; the chart still creates the password Secret it refers to:

```yaml
spec:
  managed:
    roles:
      - name: bomcensus_<release>
        ensure: present
        login: true
        passwordSecret:
          name: <release-namespace>-<release>-role
```

## Master key

The master key encrypts the CA keys and the stored credentials. **If it is lost, the PKI and all credentials are lost, and every agent and scanner has to enroll again.** Without `masterKey.value` or `masterKey.existingSecret.name`, the chart generates a key on the first install, reuses it on upgrades (`lookup`) and marks the Secret `helm.sh/resource-policy: keep`, so `helm uninstall` leaves it in place and a reinstall with the same release name uses it again. Back it up:

```sh
kubectl -n NAMESPACE get secret RELEASE-master-key -o jsonpath='{.data.master-key}' | base64 -d
```

The key is mounted as a file (`BOMCENSUS_MASTER_KEY_FILE`), not passed as an environment variable.

## Exposure and TLS

- `web` Service (8080). Without an ingress the server serves HTTPS (`web.tls`: `auto` or `manual`) with the Service DNS names plus `web.extraServerNames` in the automatic certificate; the probes use HTTPS. With `ingress.enabled=true` the chart sets `BOMCENSUS_WEB_TLS=off` and `BOMCENSUS_TRUST_PROXY=true` and the probes use HTTP; only the ingress controller should be able to reach the web port then.
- `agent` Service (8443), type `ClusterIP`, `NodePort` or `LoadBalancer`, with annotations, `loadBalancerSourceRanges` and `externalTrafficPolicy`. There is no Ingress for it: agents use mTLS and pin the server's CA, so TLS must end in the server; anything in front may only pass TCP. `externalTrafficPolicy: Local` keeps the client address that Register Key source ranges are checked against.
- `BOMCENSUS_AGENT_SERVER_NAMES` is computed by the chart from the agent Service DNS names (`<release>-agent`, `.<namespace>`, `.svc`, `.svc.<clusterDomain>`) and `agent.extraServerNames`, so it is identical on every replica. Add every name or address agents outside the cluster connect to.

Probes: startup and liveness on `/healthz`, readiness on `/readyz`. No ServiceMonitor is provided; the server has no metrics endpoint.

## In-cluster scanner

`scanner.enabled=true` installs the `bomcensus-scanner` chart (alias `scanner`; all its values can be set under `scanner.`). Its server URL defaults to `https://<release>-agent.<namespace>.svc:8443`.

Without `scanner.enrollment.token` or `scanner.enrollment.existingSecret.name`, the Job `<release>-scanner-bootstrap-<revision>` runs `bomcensus-server bootstrap-scanner`. It waits for the database and for the server to create the PKI, creates a Register Key of kind scanner (automatic approval, `scannerBootstrap.keyName`, `scannerBootstrap.maxUses`) and writes the enrollment string into the Secret `<release>-scanner-enrollment` (key `token`). The scanner pod waits for that Secret. The Job's ServiceAccount may only create Secrets in the namespace and get/update that one Secret. Running the Job again (every upgrade) keeps the Secret while its key can still enroll or is used up by a scanner that is still enrolled; otherwise it creates a new key.

The Job is a regular resource, not a Helm hook: `helm install --wait` runs post-install hooks only after every resource is ready, and the scanner cannot be ready before the Job has run.

The enrollment Secret and the Register Key stay after `helm uninstall`; delete the Secret and revoke the key in the console when the scanner is gone.

After installation register the cluster in the console (Kubernetes) with the scanner and the in-cluster connection.

## Development

`make helm-lint` lints both charts and renders the manager chart in every database mode, with and without ingress and scanner. `make helm-package` writes both packages to `dist/charts`.
